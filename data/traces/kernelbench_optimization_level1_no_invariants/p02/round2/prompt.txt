**Example: Element-wise Addition**

Input PyTorch model:

Optimized AveLang DSL kernel:
```python
import torch
import torch.nn as nn
import avelang
import avelang.language as al

@avelang.jit
def add_kernel(
    a: al.Tensor((1, 128), al.f32),
    b: al.Tensor((1, 128), al.f32),
    out: al.Tensor((1, 128), al.f32),
):
    tid = al.thread_id(0)
    if tid < 128:
        out[0, tid] = a[0, tid] + b[0, tid]

def avelang_add(a: torch.Tensor, b: torch.Tensor) -> torch.Tensor:
    assert a.is_cuda and b.is_cuda, "Tensors must be on CUDA/HIP device."
    assert a.shape == (1, 128) and b.shape == (1, 128), "Example kernel expects shape (1, 128)."

    out = torch.empty_like(a)
    add_kernel[lambda: ((1, 1, 1), (128, 1, 1))](a, b, out)
    return out

class ModelNew(nn.Module):
    def __init__(self) -> None:
        super().__init__()

    def forward(self, a, b):
        return avelang_add(a, b)
```

## AveLang DSL Critical Requirements

**Kernel Definition Requirements:**
- All `@avelang.jit` kernel functions must be defined at module top-level, never nested inside other functions or classes.
- AveLang compiles kernels at import time; runtime definition is not supported.

**Memory and Data Handling:**
- Use `al.Pointer(dtype)` for runtime-shaped buffers, then create tensor views with `al.make_tensor(pointer, dtype, layout)`.
- Use `al.make_shared((shape), dtype)` for shared memory buffers with proper synchronization.
- Use `al.range()` for device-side loops, never Python's `range()`.
- Use explicit type conversions such as `al.convert(value, al.f32)` for dtype changes.

**Launch Configuration:**
- Kernel launch syntax: `kernel[lambda: ((grid_x, grid_y, grid_z), (block_x, block_y, block_z))](args...)`.
- For BF16 precision: use BF16 computation with FP32 accumulation for numerical stability.

**Implementation Requirements:**
- Preserve the exact semantics of the target `Model.forward`.
- Keep input/output contracts compatible with `get_inputs()` and `get_init_inputs()` from the target problem.
- Do not provide a pure PyTorch eager implementation.
- Do not route final outputs through torch fallback paths such as `torch.matmul`, `torch.mm`, `torch.bmm`, `torch.Conv2d`, or equivalent eager compute.
